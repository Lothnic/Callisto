# browse source reuse: connected-browser mode for Callisto

**Research, not an implementation · 2026-11-11.** Inspected `anomalyco/browse` at commit [`3fa986601245d4f2ef9e7260f00d9f4c5a92a3b2`](https://github.com/anomalyco/browse/tree/3fa986601245d4f2ef9e7260f00d9f4c5a92a3b2) (package 0.0.16), plus Callisto's current `packages/mini` source. This is a source review; neither proposed integration was tested here.

## Conclusion

Yes: browse already implements much of the connected-Chromium product surface. It is MIT licensed and its [LICENSE](https://github.com/anomalyco/browse/blob/3fa986601245d4f2ef9e7260f00d9f4c5a92a3b2/LICENSE) permits copying, modification and distribution, provided the copyright and permission notice accompany copies or substantial portions. Preserve upstream notices and pin the revision when reusing source; check the licenses of any copied dependencies separately. This is not a determination about trademark rights or a full dependency-license audit.

The cheapest product experiment is an **optional adapter to the installed browse MCP server**, with Callisto's isolated mode retained. That gets a connected-browser option using browse's existing client interface. Its actions would be executed by browse's Playwright/Patchright-backed runtime, so this tests the combined product and **does not demonstrate that Mini drives the existing browser**. Direct Mini integration with browse's CDP relay is an attractive second experiment, but its compatibility and supported integration contract are unknown until tested.

## How a Mini backend experiment would work

Browse's [HTTP relay](https://github.com/anomalyco/browse/blob/3fa986601245d4f2ef9e7260f00d9f4c5a92a3b2/cli/src/http-api.ts) implements authenticated `/json/version` and returns a CDP WebSocket URL with session and relay-token parameters; the [CDP router](https://github.com/anomalyco/browse/blob/3fa986601245d4f2ef9e7260f00d9f4c5a92a3b2/cli/src/cdp/router.ts) mediates target visibility and routing. Browse itself connects Patchright over CDP. Callisto's `packages/mini/src/client.ts` currently launches and owns Chrome and models a session as a `chrome-launcher` process plus CDP connection. **Inference:** a separate, non-owning session/transport adapter may be feasible, but authenticated connection setup, target/session selection, CDP method compatibility, frame events and ownership/lifecycle rules must be tested against this relay; availability of a CDP endpoint is not proof that Mini can connect unchanged. Do not close the user's browser or bypass relay guardrails.

For a proof of concept, use one explicit allowlisted session on a local fixture and verify navigate, snapshot, ref click/fill, iframe handling, user tab take-back, disconnect/reconnect, and cleanup while confirming no existing user tabs are closed. Compare Callisto snapshots and actions against browse's own execute on the same pages. Report unsupported methods and target routing before offering this as a mode.

## Tradeoffs

- **Use browse as an external MCP service:** least source maintenance and easiest early prototype; install/pair browse separately, preserve its policies and test the composition. It makes connected mode dependent on another product and backend.
- **Vendor/fork upstream pieces:** product can own and customize extension/relay; requires preserving MIT notices, auditing dependencies, carrying a security-sensitive fork and tracking upstream fixes. Its [CLI package](https://github.com/anomalyco/browse/blob/3fa986601245d4f2ef9e7260f00d9f4c5a92a3b2/cli/package.json) declares Node >=22.19 and has substantial dependencies including `patchright-core`, whereas Mini currently targets Node >=20. Source modules are coupled to its protocol, session manager and build; do not assume an isolated file can be copied and work.
- **Build a fresh minimal bridge:** preserves control and a small dependency footprint, but recreates the hardest pairing, ownership and guardrail work and demands its own security review.

Recommendation: prototype the optional upstream MCP adapter first to verify the user experience, and in parallel only as a separate scoped experiment validate Mini against browse's relay. Then decide whether to keep an optional dependency, cooperate upstream, or maintain a fork. Firefox is a separate backend question; this upstream architecture and its use of `chrome.debugger` target Chromium-family browsers.
